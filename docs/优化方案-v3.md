## 1. 车辆朝向偏 90°

**根因（已确认）**：`SimCanvas.kt → drawVehicles()` 里，车身矩形是按「宽 = 车宽 w、高 = 车长 l」画的：

```kotlin
val w = (VehicleKind.WIDTH_M * scale)          // 车宽 → 局部 x
val l = (v.lengthM * scale)                     // 车长 → 局部 y
drawRoundRect(color, topLeft = Offset(cx - w/2, cy - l/2), size = Size(w, l))
rotate(deg, center) { ... }                     // deg = 行驶方向与 +x 轴夹角
```

`rotate(deg)` 是把**局部 +x 轴**对齐到行驶方向，而车长却落在**局部 +y 轴**上 → 车长轴 = 行驶方向 + 90° → 车头正好横过来。这就是你看到的"车头朝向道路左右两侧"。

**改法（推荐，最直观）**：把车长放到局部 x 轴，旋转角度不用动：

```kotlin
drawRoundRect(
    color,
    topLeft = Offset(center.x - l / 2f, center.y - w / 2f),   // 长 x 宽
    size = Size(l, w),
    cornerRadius = CornerRadius(w * 0.32f),                   // 圆角仍按车宽算
)
```

> 等价写法是保留 `Size(w, l)` 但旋转改成 `rotate(deg - 90f)`。我选前者，因为"长边 = x 轴 = 行驶方向"从代码上一眼就懂，以后不会再错第二遍。
> 简化渲染分支（`simple` 那个 `drawRect`）同样要改。

**【AI建议·补充】** 光靠矩形不好看出车头在哪。建议在车头一端加一道**浅色前挡风细条**（或两枚小前灯圆点），颜色 `Color.White.copy(alpha=0.55f)`。成本极低，但"车在往哪开"一眼可辨，观感提升明显。

## 2. 「倍速」+「统计」按钮

**要求**：在设置按钮弹出的保存/加载旁边，再加两个按钮；倍速循环 `0.5x/1x/1.5x/2x/3x/5x`；统计在最右上角显示「运行时间 + 车辆数」。

**现状**：`SimSettings.speedMultiplier` 是 **Int（只有 1/2/4）**，主循环用 `repeat(speedMultiplier.coerceIn(1,4))` 跑子步。要支持 0.5x 和 1.5x 这种**小数倍速**，必须改成浮点。

**改法**：
1. `SimSettings.speedMultiplier: Int` → `Double`（默认 1.0）。
2. 主循环改成"子步累加器"，这样 0.5x 才会真的慢放而不是卡顿：
   ```kotlin
   substepAcc += settings.speedMultiplier
   var guard = 0
   while (substepAcc >= 1.0 && guard < 8) { sim.tick(SIM_DT); substepAcc -= 1.0; guard++ }
   ```
3. `cycleSpeedMultiplier()` 改成遍历 `doubleArrayOf(0.5, 1.0, 1.5, 2.0, 3.0, 5.0)` 循环。
4. `ContextButtons` 的设置行增加两个 `SmallIconButton`：`Speed`（图标用 `Icons.Filled.Speed`）+ `BarChart`/`Assessment`（统计开关）。
5. 新增 `_showStats` StateFlow；`MainScreen` 右上角 `Alignment.TopEnd` 叠一个半透明小卡片：`运行时间 mm:ss` + `车辆数 N`（数据取自 `frame.stats.active` 和 `frame.simTime`）。

**【AI建议·补充】**
- 统计开关状态**记到设置里**（`SimSettings.showStats`），下次进来保持，不用每次点。
- 倍速到 5x 时每帧要跑 5 个子步，车多会掉帧。建议 5x 时**自动提高简化渲染阈值**（或干脆强制简化渲染），保证流畅。
- 注意存档兼容：`speedMultiplier` 类型变了，旧存档 JSON 里的整数值反序列化成 Double 是安全的（`ignoreUnknownKeys` 已开，数值类型 kotlinx 能转），但为稳妥可以在加载时做一次 `coerce`。

## 4. 目的地不能是本路口 ⚠️ 已实现

**代码里已经有了**，`TrafficSimulator.pickDestination()`：

```kotlin
fun pickDestination(originId: Long): Long? {
    val candidates = network.openNodes().filter { it.id != originId }   // ← 排除自身
    ...
    // 按 heat 加权抽样
}
```

生成车辆时 `trySpawn(junctionId, cfg)` → `pickDestination(junctionId)`，全程排除本路口。所以**这一条你不用管，v2 就是对的**。

**【AI建议·补充】** 只有一处小瑕疵：`junctionProbabilityText()` 算"目的地概率"时，分母用了**全部**开放路口的热度（含自己）。严格来说，因为自己不可能当自己的目的地，分母应该是「总热度 − 本路口热度」。建议顺手改掉，让对话框里显示的数字和实际抽样完全一致：
```
目的地概率 = heat_i / (Σheat − heat_i)
```

**【AI建议·补充】** 左上角现在有 `HintText`（操作提示）。按钮挪到左侧后会**打架**。建议：

## 6. 拥堵触发动态重路由

**要求**：新车按目的地做最快路径规划（已有）；行驶中若「前 5 秒平均速度 < 初始速度的 30%」→ 检测是否有更快路径，有则切换，切换后 10 秒内不再切换。

**现状**：
- 新车选路**已实现**：`trySpawn` 里按 `弧代价 + 到目的地的拥堵加权距离` 排序选入口弧。
- 全网络路由**每 2 秒重算一次**（`recomputeRoutes()`，拥堵感知 Dijkstra），车辆每到路口都用最新代价重新选下一段弧 —— 所以"避堵"的大框架已经在跑了。

**需要新增的**是**每辆车自己的拥堵判定 + 冷却**：

1. `Vehicle` 增字段：
   - `speedHist: DoubleArray(20)` + `histIdx`/`histCnt`：每 0.25 秒采一次速度，约 5 秒窗口；
   - `initialSpeed`：= 生成时的期望速度（判定基准）；
   - `rerouteCooldown: Double`：冷却剩余秒数。
2. `stepVehicle` 里每 0.25s 记一次速度；当**窗口满 5 秒**且 `平均速度 < 0.3 × initialSpeed` 且 `rerouteCooldown <= 0`：
   - 用**最新**的 `distToJunction[target]` 计算"从当前弧末端出发的最优下一段弧"；
   - 若该最优弧 ≠ 当前正在走的路线，且代价明显更优（比如省 ≥ 15%），则**登记为该车的新选择**，并 `rerouteCooldown = 10.0`。
3. 冷却每帧递减。

**⚠️ 必须说清楚的物理边界**：车在路上是**不能中途掉头的**（那样就不真实了）。所以"切换路径"的真实效果是——车开到**下一个路口**时改走另一条支路，而不是当场拐弯。实现上就是把"该车的下一段弧"提前锁定为更优解，并在到达路口时执行。这一点符合你要的效果（车流会绕开堵点），但"切换"发生在路口而非路段中间。

**【AI建议·补充】**
- 建议在**统计面板**里加一行「重路由次数」，方便你直观看到这个机制到底有没有在干活（调参时特别有用）。
- 阈值（5s / 30% / 10s）建议做成 **SimSettings 里的可调项**，否则不好调手感。
- 判定用"初始期望速度"当基准要小心：大型车期望速度本来就低，用它自己的期望速度做分母是合理的（相对掉速），别用全局 60km/h。

## 7. 四个 bug

### 7a + 7b：短/剩余道路点不中、删不掉（**同源**）

**根因**：`ViewModel.onTap()` 里，**先**查节点、且节点命中半径是**固定 9.0 米**：

```kotlin
val node = network.nearestNode(world, 9.0)   // ← 半径 9m，太肥
if (node != null) { ...选中节点... ; return }  // ← 命中节点就直接返回，永远轮不到选道路
...
val hit = network.hitRoad(world, 4.5)
```

- 路段 < 18m（2×9m）时，**整条路都在某个端点 9m 内** → 永远只选中节点，选不中道路本身（= 你的 7b）；
- 路段稍长一点，也必须点到"正中间那一段"才轮得到道路，偏一点就命中端点 → "足够长却点不中"（= 你的 7a）。

**改法**：把"选节点还是选道路"改成**谁近谁赢**，并且命中半径**按屏幕像素换算**（缩放自适应，大缩放下小目标也点得中）：

```kotlin
fun onTap(world: Vector2, nodeTolM: Double, roadTolM: Double) {
    val node = network.nearestNode(world, nodeTolM)
    val road = if (edit) network.hitRoad(world, roadTolM) else null
    val nd = node?.pos?.distanceTo(world)
    val rd = road?.third
    when {
        nd != null && (rd == null || nd <= rd) -> selectNode(node)   // 节点更近
        road != null -> selectRoad(road.first.id)                    // 否则选路
        else -> clearSelection()
    }
}
```
UI 侧传 `nodeTolM = camera.pxToMeters(24f)`、`roadTolM = camera.pxToMeters(28f)`。
这样：短路段点中间 → 道路更近 → 选中道路 ✅；点端点附近 → 节点更近 → 选节点 ✅。两个 bug 一起解决。

### 7c：新路与旧路交叉后，旧路一端被截断消失

**根因（已精确定位）**：`RoadNetwork.addRoad()` 打断既有道路时，调用了 `removeEdge(edgeId)`，而 `removeEdge()` **内部会顺手 `pruneOrphanNodes()`**：

```kotlin
fun removeEdge(id: Long) { edges.removeAll { it.id == id }; pruneOrphanNodes() }   // ← 元凶
```

`pruneOrphanNodes()` 会把"删边后不再连接任何道路的节点"直接删掉。于是当被交叉的那条路有个**度为 1 的死头端点**时：
1. `removeEdge` 删边 → 该端点变成孤立点 → **被 prune 删除**；
2. 紧接着重建链时 `node(toNode)?.pos` 取到 **null**；
3. 末段 `if (lastName != null && ...) chain += toNode` 判空为假 → **末段不再重建** → 旧路那一端凭空消失。

**改法**：
1. 打断链**基于坐标而非节点 id** 重建（先记录 fromPos / toPos，再删边，再按位置重建）；
2. 打断过程中**不要 prune**，`pruneOrphanNodes()` 统一挪到 `addRoad` 最末尾调一次；
3. 交点与端点距离 < `MIN_SEGMENT_M` 时，目前是"直接丢弃交点"，建议改成**合并到邻近端点**（否则会留下"看着相交、其实没打断"的假路口）。

### 7d：网格缩放后显示异常 → 改网格点

**现状**：`SimCanvas.drawGrid()` 用 `offsetX % step` 反复画**竖线 + 横线**（横线还漏了 major 判断）。缩放时步长取整误差累积，线会出现**粗细跳变/闪烁/错位**。

**改法**：改成**网格点**。在屏幕可视范围内枚举网格交点，每个交点画一个小圆点：

```kotlin
val step = RoadNetwork.GRID_M * camera.scalePxPerM
if (step < 6f) return                       // 太密不画
val startX = floor((0 - offsetX) / step).toInt()
val endX   = ceil((size.width - offsetX) / step).toInt()
for (i in startX..endX) for (j in ...) drawCircle(...)   // 半径 1~1.5px，主网格点稍大
```
点比线"抗缩放"：缩放只改变点间距，不会出现线宽跳变，视觉也更干净。

**【AI建议·补充】** 缩放很小时点会糊成一团，建议加**自适应层级**：`step < 12px` 时每 2 个点画一次、`< 6px` 时每 5 个点画一次（即只画主网格）。这样从缩到放到近景都好看。

## 8. 双指缩放瞬移

**根因（已确认）**：`Gestures.kt` 里，第二根手指落下的那一刻，`mode` 切到 `TRANSFORM`，此时 `lastCentroid` 还停留在**单指位置**，而新的 `centroid` 已经跳到**两指中点** → 一个瞬时大位移被当成平移量：

```kotlin
Mode.TRANSFORM -> {
    if (spread > 1f && lastSpread > 1f) camera.applyZoom(spread / lastSpread, centroid)
    camera.pan(centroid - lastCentroid)     // ← lastCentroid 是单指位置，产生"瞬移"
}
```

**改法**：手指数量发生变化时**重新定基准**，当次不产生位移：

```kotlin
var lastCount = 1
var transformFresh = false
...
if (count != lastCount) transformFresh = true     // 1→2 / 2→1 / 2→3 都重新基准
...
Mode.TRANSFORM -> {
    if (!transformFresh) {
        if (spread > 1f && lastSpread > 1f) camera.applyZoom(spread / lastSpread, centroid)
        camera.pan(centroid - lastCentroid)
    } else transformFresh = false
}
...
lastCount = count
```

**顺带确认**：以"两指中点"为缩放中心这一点，`CameraState.applyZoom(zoom, centroid)` **本来就是这么做的**（先记指尖世界坐标 → 缩放 → 反向补偿 offset），逻辑是对的，只是被那个瞬移掩盖了。修完瞬移，缩放中心就自然落在两指中点。

## 9. 曲线按钮图标换成「一段圆弧」

**现状**：曲线工具用的是 `Icons.Filled.Gesture`——那是一坨**带好几个圈**的手势曲线，确实"绕圈过多"。

**改法**：自定义一个**单段圆弧**矢量图标（不依赖具体图标库里有没有），一段二次贝塞尔即可，干净利落：

```kotlin
val ArcIcon: ImageVector by lazy {
    ImageVector.Builder(
        name = "CurveArc", defaultWidth = 24.dp, defaultHeight = 24.dp,
        viewportWidth = 24f, viewportHeight = 24f,
    ).apply {
        path(
            stroke = SolidColor(Color.Black),
            strokeLineWidth = 2f,
            strokeLineCap = StrokeCap.Round,
        ) {
            moveTo(4f, 19f)
            quadraticBezierTo(4f, 7f, 19f, 7f)   // 单段圆弧，半圆感
        }
    }.build()
}
```
然后 `BottomBar` 里曲线态的图标从 `Icons.Filled.Gesture` 换成 `ArcIcon`；直线态保持 `Icons.Filled.Remove`（一横）——一横 + 一弧，语义对比很清晰。

> 备选：`Icons.Filled.RoundedCorner`（现成的圆角符号）。但它本质是"一个方角"，弧形感弱于自定义矢量。我推荐自定义。
